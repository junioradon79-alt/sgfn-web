# Audit complet SGNF — Sécurité, Logique, Qualité

**Date :** 24 juillet 2026
**Périmètre :** dépôt `sgfn-web` (front Next.js, 195 fichiers TS/TSX) + backend Supabase prod (`bvdzrhvbiglwrhzpmuwy` : ~46 tables, 87 migrations, 7 edge functions locales).
**Méthode :** lecture directe du code sensible + interrogation **en lecture seule** de la production (policies, définitions de fonctions réelles) + **preuves par simulation RLS** (`set role` + `request.jwt.claims` en transaction annulée) pour tout ce qui est affirmé comme une fuite. Aucune écriture en base.

---

## 0. Verdict global

La posture de sécurité de base est **solide et cohérente** : RLS activée partout, fonctions privilégiées durcies, escalade de privilèges fermée, webhooks de paiement non falsifiables. Les défauts trouvés ne sont pas des trous béants mais **deux fuites de lecture par sur-permissivité** (des policies `using(true)`/`peut_contacter` trop larges), plus des points d'hygiène (versionnement partiel des edge functions, code mort piégeux).

| Gravité | Nombre | Sujets |
| --- | --- | --- |
| 🔴 Élevée | 1 | Exposition anonyme de `lotissements` (GPS exacts, TF, scans) |
| 🟠 Moyenne | 1 | Fuite PII inter-profils via `peut_contacter` (tout acquéreur lit tous les profils) |
| 🟡 Faible | 3 | Edge functions partiellement versionnées ; `initier-paiement` sans contrôle de propriété ; code mort « deux clients Supabase » |
| ⚪ Mineure | 3 | Types maintenus à la main ; 4 erreurs eslint préexistantes ; rappels d'état (secrets CinetPay, invitations expirées) |

## 1. 🔴 Exposition anonyme de la table `lotissements` (GPS exacts compris)

**Constat.** La policy `lotissements_public_read` est `FOR SELECT TO public USING (true)` — donc **un utilisateur non connecté (anon) lit l'intégralité de la table `lotissements`**, toutes colonnes comprises :

`tf_numero`, `livre_foncier`, `centre_cadastral`, `reference_plan`, `cedant`, `beneficiaire_immatriculation`, `geometre_expert`, `cabinet_geometre`, `pv_numero_enregistrement`, `pv_identification_physique_scan_url`, `derogation_documents_motif`, et surtout **`latitude` / `longitude` exactes**.

**Preuve (simulation anon, prod, transaction annulée) :**
```
lotissements lus par anon : 2/2
exemple lisible sans login : Koelea-Accor revu | GPS=5.4834,-4.0247
```

**Pourquoi c'est grave.** Cela **contredit frontalement le principe de confidentialité posé au §4.2 du document directeur** : « coordonnées exactes privées ; le public voit un cercle flou de 500 m ». Tout le travail de floutage GPS (`lat_approx`/`lng_approx` arrondis ~110 m, vue `annonces_publiques`) est contourné au niveau lotissement : les coordonnées précises sortent en clair, sans authentification, avec les références cadastrales et une URL vers le scan du PV d'identification physique.

**Correctif recommandé.** Ne **pas** exposer la table brute à anon. Deux options :
- remplacer la policy par une **vue publique restreinte** (sur le modèle de `annonces_publiques`) n'exposant que `nom`, `village`, `commune`, `district`, `nb_ilots`, `nb_lots` — jamais GPS/TF/scans ;
- ou, si le besoin public n'existe pas réellement, **retirer `lotissements_public_read`** et ne garder que `lotissements_read` (`auth.uid() IS NOT NULL`) + `lotissements_admin_all`.

> Déjà repéré comme « sujet distinct » en mémoire agent (`fusion_amenageur_operateur_et_scope`), jamais soldé. `ilots` porte la même policy `using(true)` mais n'expose que `id, lotissement_id, numero` → **bénin**, à laisser.

## 2. 🟠 Fuite PII inter-profils : tout acquéreur lit tous les profils

**Constat.** La policy de lecture des profils est :
```
profiles_contact_read : SELECT USING (est_admin() OR id = auth.uid() OR peut_contacter(id))
```
Or `peut_contacter()` (SECURITY DEFINER) contient :
```sql
if v_mon_groupe in ('amenageur','proprietaire','acquereur') then return true; end if;
```
→ pour un `acquereur`, `peut_contacter(n'importe qui) = true`. Comme **`acquereur` est le groupe attribué par défaut à toute auto-inscription** (`handle_new_user` : `coalesce(v_groupe,'acquereur')`), n'importe qui peut créer un compte et lire **tous** les profils.

**Preuve (simulation acquéreur, prod) :**
```
Acquéreur 3052d084…  |  profils visibles = 20 / 20  →  FUITE CONFIRMEE
```

Les colonnes lues incluent `nom_complet` **et `telephone`** de tous les utilisateurs — administrateurs, chefferies, opérateurs, commissaires compris.

**Pourquoi c'est un problème.** Le modèle métier (§4.2) veut que la mise en relation soit **manuelle et intermédiée par SGNF**, sans coordonnées publiées automatiquement. Ici, le numéro de téléphone de chaque acteur est moissonnable par un simple compte gratuit. Impact réel aujourd'hui **limité** (20 profils, 3 acquéreurs), mais **structurel** : il grandit avec chaque inscription.

**Correctif recommandé.** Retirer `acquereur` (et les groupes legacy `amenageur`/`proprietaire`) de la branche « return true » de `peut_contacter`. Un acquéreur n'a besoin de lire aucun profil tiers pour son parcours (la mise en relation passe par l'admin) ; s'il en faut un, le restreindre aux profils réellement liés à une de ses transactions, comme le fait déjà proprement la branche `commissaire` (jointure sur `litiges`/`attributions`).

## 3. 🟡 Edge functions partiellement versionnées (angle mort d'audit)

Le dossier local `supabase/functions/` contient **7** fonctions, mais le front en appelle plusieurs qui **n'ont aucune source dans le dépôt** :

| Appelée par le front | Présente en local ? |
| --- | --- |
| `telecharger-document` | ❌ **absente** — garde l'accès aux PDF stockés |
| `analyser-document-ia` | ❌ absente |
| `convertir-plan-cad` | ❌ absente |
| `publier-annonce` | ❌ absente |
| `initier-paiement`, `payer-consultation-qr`, `verification-qr` | ✅ |

**Risque.** `telecharger-document` est une fonction **sensible** (elle sert des documents fonciers stockés — son contrôle d'accès conditionne toute la confidentialité du coffre-fort documentaire) et elle est **inauditables depuis le dépôt**. Par ailleurs, la présence de 7 fonctions locales donne une **fausse impression d'exhaustivité** : rien n'indique qu'il en manque. Enfin, sans source versionnée, ce code est **perdu** en cas de perte du projet Supabase.

**Correctif recommandé.** Rapatrier toutes les edge functions déployées dans `supabase/functions/` (`supabase functions download`), les committer, et faire de ce dossier la source de vérité. Auditer en priorité le contrôle d'accès de `telecharger-document`.

> ⚠️ Corollaire : les 7 sources locales **peuvent elles-mêmes être périmées** vis-à-vis du déployé (ex. l'en-tête CORS de `initier-paiement` local — `authorization, content-type` — n'inclut pas `x-client-info`, alors que le correctif CORS du 11/07 l'ajoutait ; la version locale semble antérieure au fix). Ne pas conclure sur le déployé à partir du local pour ces fichiers.

## 4. 🟡 `initier-paiement` — pas de contrôle de propriété du paiement

**Constat (source locale).** La fonction exige un utilisateur authentifié, puis récupère le paiement par `paiement_id` avec le client **service_role** (contourne la RLS). Elle lit `acquereur_id`… mais **ne le compare jamais** à l'appelant, et ne vérifie pas qu'il est admin. Tout utilisateur connecté peut donc lancer l'initiation de paiement d'un `paiement_id` arbitraire.

**Impact réel : faible.** Le montant est lu **en base**, pas fourni par le client (pas de manipulation de somme) ; la réponse ne renvoie aucune donnée sensible (juste l'URL CinetPay + txId) ; les `paiement_id` sont des UUID non énumérables ; le pire effet est de basculer un paiement `en_attente → initie` (récupérable). Ce n'est pas une faille critique, mais **le contrôle d'autorisation manque**.

**Correctif recommandé.** Après lecture du paiement, exiger `paiement.acquereur_id = mon_attributaire_id(appelant)` **ou** appelant admin. (À valider d'abord contre la version **déployée**, cf. §3.)

## 5. 🟡 Code mort « deux clients Supabase » — bug neutralisé mais piège latent

Le projet a deux fabriques de client Supabase :
- `src/utils/supabase/client.ts` — `createBrowserClient` (`@supabase/ssr`, session en **cookie**) → utilisé par **65 fichiers** (le bon).
- `src/lib/supabase.ts` — `createClient` (`@supabase/supabase-js`, session en **localStorage**) → en export statique, ne voit jamais la session cookie → **requêtes anonymes** → sous RLS, **0 ligne renvoyée en silence** (« base vide »).

**Bonne nouvelle :** le client anon n'est importé que par **3 services** (`services/auth.ts`, `services/dashboard.ts`, `services/profile.ts`) qui sont eux-mêmes **du code mort** — aucun fichier ne les importe. Le bug documenté en mémoire (`deux_clients_supabase_cookie_vs_localstorage`) n'est donc **plus actif** en pratique.

**Mais le piège demeure :** `@/lib/supabase` est le chemin d'import le plus « évident ». Tout nouveau code qui l'utilise fera des requêtes anonymes renvoyant 0 ligne **sans erreur**.

**Correctif recommandé.** Supprimer les 3 services morts, puis soit supprimer `src/lib/supabase.ts`, soit le transformer en simple ré-export du client cookie pour neutraliser le piège définitivement.

## 6. ⚪ Points mineurs

- **Types maintenus à la main.** `database.types.ts` est patché manuellement (pas de script `supabase gen types` dans `package.json`). Une divergence `Insert`/`Update` a déjà causé un bug le 22/07 (leçon §9 du doc directeur). Rappel : régénérer plutôt que patcher.
- **4 erreurs eslint préexistantes** (`react-hooks/set-state-in-effect` / « impure function during render ») dans 2 fichiers. Dette mineure, non bloquante ; `tsc --noEmit` passe **proprement** et `console.log` = **0** dans `src/`.
- **XSS :** `dangerouslySetInnerHTML` n'apparaît que 2 fois, uniquement pour injecter des **CSS d'impression statiques** (`printCss`), jamais de la donnée utilisateur → sans risque.
- **Rappels d'état (déjà connus, hors code) :** secrets CinetPay absents (paiement en ligne inerte, dette #2) ; 2 invitations expirées à réémettre (Ebimpe / propriétaire terrien, dette #13).

## 7. Ce qui a été vérifié SAIN (à valoriser)

Ces contrôles ont été testés et **confirmés corrects** — ils constituent le socle solide de la plateforme :

| Contrôle | Résultat (vérifié en prod) |
| --- | --- |
| **Couverture RLS** | **100 %** — 0 table du schéma `public` sans RLS |
| **Durcissement SECURITY DEFINER** | **100 %** — 0 fonction sans `search_path` fixé (protège du détournement de search_path) |
| **Escalade de privilèges** | Fermée : groupe dérivé de l'**invitation** (`handle_new_user`, défaut `acquereur`) ; `with_check` + trigger `trg_protect_profile_privileged_columns` bloquent l'auto-promotion `groupe`/rattachements/`actif` ; contrainte `invitations_check` **fail-closed** (un acquéreur ne peut pas porter d'`attributaire_id`) |
| **Webhooks CinetPay** (`confirmer-paiement`, `confirmer-consultation-qr`) | Ne font **jamais** confiance au callback : re-vérifient le paiement via l'API CinetPay (`/v2/payment/check`) avant toute écriture ; **idempotents** ; échouent **fermé** si les secrets manquent |
| **`verification-qr`** (publique) | Verdict calculé **côté serveur**, paywall appliqué **côté serveur** ; document révoqué annoncé **gratuitement** en charge réduite (ni contenu payant ni motif) |
| **`generation-document`** | Garde fail-closed : exige `service_role` **ou** `x-hook-secret` (le simple `verify_jwt` ne suffirait pas — la clé anon est aussi un JWT valide, et le code le sait) |
| **Montants financiers** | Lus **en base**, jamais fournis par le client (`creer_cession`, `initier-paiement`) ; `creer_cession` réservé admin/opérateur et **lève une exception** plutôt que de facturer au hasard |
| **`marquer_paiement_recu`** | Bien que non-SECURITY DEFINER, un appel direct par un non-admin est **bloqué par la RLS** de `paiements` (écriture 0 ligne) — pas de confirmation de paiement sans payer |

## 8. Priorisation des correctifs

1. **`lotissements` anon (§1)** — le plus impactant (GPS exacts publics). Migration RLS + vue publique restreinte.
2. **`peut_contacter` / acquéreur (§2)** — fuite PII structurelle. Une ligne à retirer dans la fonction.
3. **Rapatrier + auditer `telecharger-document` (§3)** — lever l'angle mort sur l'accès aux PDF.
4. Contrôle de propriété sur `initier-paiement` (§4), nettoyage du code mort (§5).

> Les correctifs 1 et 2 touchent des policies/privilèges de **production** : ils sortent du périmètre de cet audit (lecture seule) et **attendent une décision explicite** avant application.

## 9. Correctifs préparés (migrations écrites et testées, NON appliquées)

Deux migrations ont été écrites et **validées contre la production en transaction auto-annulée** (pattern `RAISE EXCEPTION` final — aucune écriture persistée). Elles restent à **appliquer sur décision**.

### `20260724160000_fix_audit_lotissements_anon_columns.sql` (fuite #1)
Approche : **privilèges au niveau colonne** (pas de vue ni de changement front). `REVOKE SELECT … FROM anon` puis `GRANT SELECT (id, nom, village, commune, district, superficie_texte, nb_ilots, nb_lots) TO anon`. La policy RLS `using(true)` (niveau ligne) est conservée ; seules les colonnes sensibles deviennent illisibles pour anon.
Justifié par : monterrain-web ne lit jamais la table (vues seules) ; `/lotissements/[id]` est authentifié (`AppShell`) ; seuls `generateStaticParams` (`id`) et `usePublicStats` (`id,nom`) lisent en anon — colonnes conservées.
**Résultat du test (prod, annulé) :** `anon.id=✓ anon.nom=✓` (conservés), `anon.latitude=✗ anon.tf_numero=✗ anon.pv_scan=✗` (bloqués), `authenticated.latitude=✓` (inchangé).

### `20260724161000_fix_audit_peut_contacter_acquereur.sql` (fuite #2)
Approche : réécriture de `peut_contacter` — un acquéreur ne voit plus que **l'administration SGNF (`admin`) + les personnes avec qui il partage déjà une conversation** (pour l'affichage des noms en messagerie). Groupes dépréciés `amenageur`/`proprietaire` : refus par défaut. Branches `admin`/`commissaire` inchangées.
**Résultat du test (prod, annulé) :** un acquéreur passe de **20/20 profils à 5** (self + 4 admins) sans conversation, **7** avec conversation (partenaire non-admin **toujours visible → messagerie non cassée**).

> Aucune de ces deux migrations n'a été exécutée sur la base. Application sur validation.
